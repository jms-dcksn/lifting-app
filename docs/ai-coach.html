Targets across a program week (#208)

Ask “What are my targets across this week?” or “What should I aim for next week?” Coach calls the existing nextWorkout tool with current_week or upcoming_week. It returns every program day in order. These are training-program weeks, not Monday–Sunday reporting windows or a calendar schedule.

  Ask[User asks for workout targets] --> Scope{Scope}
  Scope -->|omitted or next_workout| Next[Existing next workout: Home and planner parity]
  Scope -->|current_week or upcoming_week| Week[Resolve program week from finished count or open saved week]
  Week --> End{Beyond programmed block?}
  End -->|Yes| Empty[beyond_program: no invented week]
  End -->|No| Days[Every ordered program day]
  Days --> Reuse[Next or open occurrence: reuse saved choices and evidence]
  Days --> Others[Other days: shared resolveWorkoutSlots and recorded history]
  Reuse --> Result[Prescriptions, exact identity, status and available targets]
  Others --> Result
  Result --> Complete[Completed or unknown completion: withhold targets]
  Result --> Estimate[Future: current-history estimates, no simulated gains]

In a three-day program, seven completed sessions put the next workout in program week 3. The current scope shows A, B and C; the upcoming scope shows program week 4. After the final programmed week, weekly retrieval returns an empty list with beyond_program. Default next-workout calls retain their existing response and behavior. Exact lines from src/lib/program-week-workouts.ts:

  const next = await loadNextWorkout(client, userId, program);
  const week = next.week + (scope === "upcoming_week" ? 1 : 0);

A · Completed

Current prescription details remain visible. Targets are null. These details do not reconstruct what was prescribed or lifted then.

B · Open or upcoming

The actual next occurrence retains its planner swap. An open workout keeps its stored day/week/station, deload flag and pre-start evidence. Reads preserve typed inputs and saved sets.

C · Upcoming estimate

Resolve this slot's own sets, reps, RIR, rest, phase and current Fluid changes. Do not assume B was completed successfully or add another progression step. Workout-only swaps stay on their original occurrence.

The same slot composer serves Home/planner and weekly projections. Different prescriptions for the same exercise stay separate, including recovery phases and supported effort reductions. Unknown exercise/equipment or insufficient evidence leaves a null target. Source excerpt from src/lib/program-week-workouts.ts:

    const slots = isNext ? next.slots : resolveWorkoutSlots({ program, day, week, choices: {}, logged: [],
      adaptations, targetHistory: history, catalog: next.catalog, stats: next.stats, bodyweight: next.bodyweight,
      defaultRestSeconds: next.defaultRestSeconds });

Completion comes from saved owner/program/week/day identity. If program position passed a day but its completion metadata is missing, status is unknown and targets stay null. No active program returns no_active_program. Reads create no sessions, cookies, adaptations or notifications. Deterministic tests cover loaders, owner filters, capped pages, phases, swaps, open workouts, missing data and the real agent tool loop with a scripted model. They do not evaluate a live model's routing or prose.

Hypothetical e1RM — the calculator (#205)

Ask “If I bench 100 kg total for 5 reps with 2 RIR, what is my estimated max?” Coach calls calculateE1rm and explains the returned estimate: about 123.3 kg total external load. Any lift can be labeled, even with no program or logged history. The tool uses the existing RPE/RIR model; no model arithmetic, catalog lookup or database access is involved.

  User[User-supplied hypothetical set] --> Validate{Valid numeric inputs?}
  Validate -->|No| Invalid[invalid_input: ask for correction]
  Validate -->|Yes| RepOnly{Rep-only movement?}
  RepOnly -->|Yes| Unavailable[unavailable: no load-based estimate]
  RepOnly -->|No| Context{Load, reps, unit and convention complete?}
  Context -->|No| Ask[needs_input: ask for missing context]
  Ask --> User
  Context -->|Yes| Load[Canonical effectiveLoad: bodyweight required where applicable]
  Load --> Positive{Effective load and result finite and positive?}
  Positive -->|No| Invalid
  Positive -->|Yes| Result[estimated: computeE1rm, inputs, unit, basis and assumptions]
  Result --> Reply[Coach explains hypothetical estimate and RIR default]

The sign and context matter. The schema rejects malformed numbers; the domain function asks for missing fields before calculating. These are exact source lines from src/lib/agent/tools/calculate-e1rm.ts:

  const load = effectiveLoad({ equipment: isBodyweight ? "bodyweight" : "barbell" }, weight, input.bodyweight ?? null);
  const rir = input.rir ?? 2;
  const estimate = load == null || load <= 0 ? NaN : computeE1rm(load, reps, rir);

External and dumbbell load

Barbell means total load including the bar. Dumbbells use one hand's load and return a per-hand estimate; never double it. Explicit kg/lb pass through without changing app storage.

Machines

Use this station's logged load. Stack labels and leverage do not make the estimate transferable to another machine or free weights.

Bodyweight and assistance

Supply bodyweight plus added load (zero if unweighted; negative for assistance) in the same unit. Return total-system-load e1RM, not added weight or assistance. Missing bodyweight asks for clarification; the tool never substitutes current profile weight.

Honest limits

Omitted RIR defaults to 2 and is disclosed. Above 12 effective reps the existing curve extrapolates, so the answer flags greater uncertainty. Rep-only exercises have no load-based e1RM. A hypothetical estimate is not a measured max, logged set, PR, target change or notification.

Tests cover canonical numeric parity, units, signed assistance, missing context and invalid inputs, plus real registered-tool calls through a scripted agent turn. Authored eval cases distinguish hypothetical questions from logged-history questions, which still use exerciseReview. Scripts verify orchestration, not live-model compliance; no paid live eval ran.

Exception eligibility — implemented foundation (#210)

The policy takes a current, authorized history snapshot and returns typed candidates. It runs no model, sends no notification and changes no workout. The inbox and conversation journey come later. The engine still owns every number.

1. Keep context exact

Match slot, exercise, equipment instance, phase, adaptation and prescription. Reject recovery, stale or incomplete evidence.

2. Require a meaningful signal

Two first-set effort misses; two independently reduced rep-floor targets; confirmed plateau; or four-exposure decline. Significant pain stays session-level.

3. Return one candidate per slot

Group overlapping lift signals with source session/set IDs and evidence dates. Every action is recommended; none is asserted to be applied.

  Series --> Context{Current context matches and evidence is fresh?}
  Context -->|No| Quiet[No candidate]

The two load-reduction causes differ. One below-range set can quietly recalibrate the next target. Two such sets qualify only if each independently calls for a lower load. Two consecutive first-set RIR misses use the existing one-increment reduction. Hard back-off sets do not count. The Coach proposal exposes that cause in loadReductionReason; its Do first/Also ranking does not choose alerts.

The path of one question

You tap the speech-bubble button with two four-point sparkles (or open /coach). The browser sends your words to a server route. That route proves you are signed in, writes your message to Postgres, asks LangChain to think, and streams the reply back. LangChain may call a tool. Each tool is a thin wrapper around an existing loader. LangSmith records the trace so you can see which tools ran.

The bubble signals conversation; the sparkles identify AI assistance. The icon inherits the button color, and the button keeps its accessible name, Coach.

Why a composite key

agent_message
(thread_id, user_id)
→
agent_thread
(id, user_id)

RLS checks a row's own user_id. It cannot see whose thread thread_id names. The composite foreign key makes Postgres reject a message aimed at another user's thread.

Who owns what

If the agent computed a squat target itself, Home and the session screen would drift. So the engine keeps the math. The agent only narrates.

Engine

Numbers, prescriptions, stalls, Last / 21-day / chart summaries, sessionTarget().

Agent

Language, which tool to call, citing the source, refusing diagnosis and writes.

Recovery targets match recovery effort

The nextWorkout tool and active session share the same target engine. At four or more reps in reserve, it recalculates load from recent performance instead of adding a rep or weight. It keeps the prior reps inside the programmed range, rounds to an achievable load, and caps it at the prior load. Phase names do not control this rule; both Deload and Recovery prescriptions work.

1. Recent performance

150 lb × 7 at 1 RIR

2. Load model

Estimate strength, then solve for 7 reps at 4 RIR.

3. Shared target

135 lb × 7 at 4 RIR

Bodyweight work converts total load back to added or assisted load. Unknown bodyweight means no recovery load suggestion. Missing historical RIR uses two. Below four target RIR, normal progression stays unchanged. The agent narrates the returned numbers; it does not calculate a separate deload percentage.

src/lib/agent/thread.ts — the id rule

async function openThread(supabase: Client, userId: string, text: string) {
  const id = parseThreadId(uuid7());
  if (!id) throw new Error("Unable to create agent thread");
  const title = threadTitleFromUserText(text);
  const created = await supabase.from("agent_thread").insert({ id, user_id: userId, title });
  if (created.error) throw new Error(created.error.message);
  try {
    const userMessage = await saveMessage(supabase, userId, id, userText(text));
    return { thread: { id, title, updatedAt: userMessage.createdAt }, userMessage };
  } catch (error) {
    await supabase.from("agent_thread").delete().eq("id", id).eq("user_id", userId);
    throw error;
  }
}

The thread row exists only once you send. If the first message cannot be saved, the row is deleted again before the error reaches you.

src/lib/agent/chat-state.ts — the title rule

export function threadTitleFromUserText(text: string): string {
  const collapsed = text.replace(/\s+/g, " ").trim();
  // Code points, not UTF-16 units, so an emoji at the cut never leaves a lone surrogate.
  return Array.from(collapsed).slice(0, TITLE_LIMIT).join("") || "New chat";
}

TITLE_LIMIT is 80. The migration backfilled older threads with the same rule in SQL.

src/lib/agent/chat-handler.ts — the body must name its thread

function parseTurnRequest(body: unknown): TurnRequest | null {
  if (!body || typeof body !== "object" || !("threadId" in body)) return null;
  const { text, threadId } = body as { text?: unknown; threadId: unknown };
  const trimmed = typeof text === "string" ? text.trim() : "";
  if (!trimmed) return null;
  if (threadId === null) return { kind: "new", text: trimmed };
  const id = parseThreadId(threadId);
  return id ? { kind: "continue", threadId: id, text: trimmed } : null;
}

src/lib/agent/markdown.ts — one source, then the body

const SOURCE_LINE = /^(?:\*\*)?Source:\s*(.+?)(?:\*\*)?\s*$/i;

export function splitCoachReply(text: string): { body: string; sources: string[] } {
  const sources: string[] = [];
  const kept: string[] = [];
  for (const line of text.split("\n")) {
    const match = line.trim().match(SOURCE_LINE);
    if (!match) {
      kept.push(line);
      continue;
    }
    const source = match[1].replace(/\*\*/g, "").trim();
    if (source) sources.push(source);
  }
  return { body: kept.join("\n").replace(/\n{3,}/g, "\n\n").trim(), sources };
}

export function availableCoachIntervention(episode: CoachEpisode, suggestion: PendingSuggestion | null) {
  if (episode.family !== "lift_performance" || episode.state !== "open" || episode.validity !== "current"
    || episode.snoozeSourceIds !== null || !suggestion) return null;
  const signal = episode.evidence?.candidate.signals.find(s => s.reason === "confirmed_plateau");
  if (!signal || signal.action !== suggestion.action) return null;
  if (signal.action === "rep_change" && (signal.repBand.repMin !== suggestion.repBand?.repMin
    || signal.repBand.repMax !== suggestion.repBand?.repMax)) return null;
  return suggestion;
}

/** An explicit Discuss click answers the owned seed without inserting another user message. */
async function discussReview(supabase: Client, userId: string, threadId: ThreadId) {
  const { data: link, error } = await supabase.from("coach_episode_thread").select("seed_message_id")
    .eq("user_id", userId).eq("thread_id", threadId).maybeSingle();
  if (error) throw Error("Coach review is unavailable. Please retry.");
  if (!link) return null;
  const [thread, messages] = await Promise.all([
    findThread(supabase, userId, threadId), loadTranscript(supabase, userId, threadId),
  ]);
  const seed = messages[0];
  if (!thread || messages.length !== 1 || seed?.id !== link.seed_message_id || seed.role !== "user") return null;
  return { thread: { ...thread, updatedAt: seed.createdAt }, userMessage: seed };
}
