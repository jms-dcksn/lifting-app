How the in-app Coach talks to the ledger

This page teaches the shipped Slice 0 agent, multi-thread chat, and Slice 1 screen context plus navigation. The deterministic Track Coach still owns the numbers. The agent is a talking layer on top of loaders you already have.

The path of one question

You tap the chat button (or open /coach). The browser sends your words to a server route. That route proves you are signed in, writes your message to Postgres, asks LangChain to think, and streams the reply back. LangChain may call a tool. Each tool is a thin wrapper around an existing loader. LangSmith records the trace so you can see which tools ran.

“How was this week?”

The model is not allowed to invent adherence. It must call weeklyCoach, which calls loadCoachUi — the same function Track Coach uses. The answer is markdown. It ends with one Source: line. The sheet lifts that line out of the bubble so it is not repeated under every figure. The sheet opens your most recent chat at its latest message. The composer stays pinned. Full screen opens the same chat at /coach?thread=<id>.

Full transcript vs last N

Every message is saved. Reload /coach?thread=<id> and you see the whole thread, including tool-call parts. The model does not get the whole thread. Each turn takes the system prompt plus the last CONTEXT_MESSAGE_LIMIT messages (20). If that window is still large, old tool JSON is stubbed out first. User and assistant sentences stay. There is no summarizer and no embeddings.

Postgres (UI)

All turns, all tool parts. Many threads per user. History lists the newest 50.

Model window

System prompt + last 20. Prefer dropping old tool results before dropping words.

Many chats, one id each

You can keep many chats. Opening the sheet or tapping New chat saves nothing. That screen is a draft. Your first message is what creates the thread. The server picks the id with uuid7() and titles the thread from your words. The same id goes to LangSmith as metadata.thread_id, so every trace from one chat lands in one LangSmith thread. Postgres still holds the transcript. There is no checkpointer.

Every later message sends that id back. The server checks that the thread is yours before it writes anything. Someone else's id gets a 404, and the model never runs. A request without the threadId key is a 400, so a client cannot fall back to a hidden default thread.

The browser keeps the chat in one reducer with three screens. The sheet starts in Loading because it fetches when it opens. /coach renders its snapshot on the server, so it starts in Chat. While a turn streams, Chat history, New chat, and Full screen are disabled, so the streaming reply always belongs to the chat on screen. New chat swaps in a draft without leaving Chat.

Why a composite key

agent_message
(thread_id, user_id)
→
agent_thread
(id, user_id)

RLS checks a row's own user_id. It cannot see whose thread thread_id names. The composite foreign key makes Postgres reject a message aimed at another user's thread.

Who owns what

If the agent computed a squat target itself, Home and the session screen would drift. So the engine keeps the math. The agent only narrates.

Engine

Numbers, prescriptions, stalls, Last / 21-day / chart summaries, sessionTarget().

Agent

Language, which tool to call, citing the source, refusing diagnosis and writes.

Recovery targets match recovery effort

The nextWorkout tool and active session share the same target engine. At four or more reps in reserve, it recalculates load from recent performance instead of adding a rep or weight. It keeps the prior reps inside the programmed range, rounds to an achievable load, and caps it at the prior load. Phase names do not control this rule; both Deload and Recovery prescriptions work.

1. Recent performance

150 lb × 7 at 1 RIR

2. Load model

Estimate strength, then solve for 7 reps at 4 RIR.

3. Shared target

135 lb × 7 at 4 RIR

Bodyweight work converts total load back to added or assisted load. Unknown bodyweight means no recovery load suggestion. Missing historical RIR uses two. Below four target RIR, normal progression stays unchanged. The agent narrates the returned numbers; it does not calculate a separate deload percentage.

src/lib/agent/thread.ts — the id rule

async function openThread(supabase: Client, userId: string, text: string) {
  const id = parseThreadId(uuid7());
  if (!id) throw new Error("Unable to create agent thread");
  const title = threadTitleFromUserText(text);
  const created = await supabase.from("agent_thread").insert({ id, user_id: userId, title });
  if (created.error) throw new Error(created.error.message);
  try {
    const userMessage = await saveMessage(supabase, userId, id, userText(text));
    return { thread: { id, title, updatedAt: userMessage.createdAt }, userMessage };
  } catch (error) {
    await supabase.from("agent_thread").delete().eq("id", id).eq("user_id", userId);
    throw error;
  }
}

The thread row exists only once you send. If the first message cannot be saved, the row is deleted again before the error reaches you.

src/lib/agent/chat-state.ts — the title rule

export function threadTitleFromUserText(text: string): string {
  const collapsed = text.replace(/\s+/g, " ").trim();
  // Code points, not UTF-16 units, so an emoji at the cut never leaves a lone surrogate.
  return Array.from(collapsed).slice(0, TITLE_LIMIT).join("") || "New chat";
}

TITLE_LIMIT is 80. The migration backfilled older threads with the same rule in SQL.

src/lib/agent/chat-handler.ts — the body must name its thread

function parseTurnRequest(body: unknown): TurnRequest | null {
  if (!body || typeof body !== "object" || !("threadId" in body)) return null;
  const { text, threadId } = body as { text?: unknown; threadId: unknown };
  const trimmed = typeof text === "string" ? text.trim() : "";
  if (!trimmed) return null;
  if (threadId === null) return { kind: "new", text: trimmed };
  const id = parseThreadId(threadId);
  return id ? { kind: "continue", threadId: id, text: trimmed } : null;
}

Name resolution — exerciseReview

The user says a lift. They do not know the catalog id. The resolver stays in process, over the merged catalog, and asks when two lifts stay close. A word that matches nothing, such as “face pulls”, is not found. If the phrase is an exact catalog name and that row is logged, or nothing is logged, that row wins. Otherwise a logged station can beat the empty template: “hack squat” with only a Nautilus history resolves to that station, and asks when Cybex has sets too.

The expanded machine catalog keeps cable and lever pulldowns separate. With no logged station preference, “lat pull down” asks which one; “cable lat pull down” and “machine lat pull down” select their respective templates. Choosing a machine brand and loading type creates an owned Supabase variant through the existing station flow. Each new machine requires calibration; old custom exercise histories remain separate.

src/lib/agent/markdown.ts — one source, then the body

const SOURCE_LINE = /^(?:\*\*)?Source:\s*(.+?)(?:\*\*)?\s*$/i;

export function splitCoachReply(text: string): { body: string; sources: string[] } {
  const sources: string[] = [];
  const kept: string[] = [];
  for (const line of text.split("\n")) {
    const match = line.trim().match(SOURCE_LINE);
    if (!match) {
      kept.push(line);
      continue;
    }
    const source = match[1].replace(/\*\*/g, "").trim();
    if (source) sources.push(source);
  }
  return { body: kept.join("\n").replace(/\n{3,}/g, "\n\n").trim(), sources };
}

export function parseScreenContextFromPath(pathname: string): AgentScreenContext {
  const sessionMatch = pathname.match(SESSION_PATH);
  const openSessionId = sessionMatch && !RECAP_PATH.test(pathname)
    ? decodeURIComponent(sessionMatch[1]) : null;
  const exerciseMatch = pathname.match(HISTORY_PATH);
  const focusedExerciseId = exerciseMatch ? decodeURIComponent(exerciseMatch[1]) : null;
  return { pathname, activeProgramId: null, openSessionId, focusedExerciseId };
}

A missing trend is said out loud

One e1RM point is not a trend. The system prompt tells the model to say so when exerciseReview returns a gap, a null delta, or fewer than two chart points, and then to report the last session if one exists. The same rule covers the other read tools: Coach text that says “not available”, a null next-workout target, and no active program. Each tool description names the field that means “missing”.

src/lib/agent/prompt.ts — say the comparison is missing

- One logged value is not a trend. If the user asked how something is changing and the tool has no comparison, say that no trend is available, then give the last fact the tool did return.
  - exerciseReview: recent21Days is null, recent21Days.kind is "gap", recent21Days.delta is null, or chartLast8 has fewer than two points.

function gradeResolved(results: Record<string, unknown>[], exerciseId: string) {
  if (results.some((result) => result.exerciseId === exerciseId)) {
    return { score: 1, comment: `found ${exerciseId}` };
  }
  return { score: 0, comment: `expected ${exerciseId}; saw ${results.map(describeResult).join(" | ")}` };
}
