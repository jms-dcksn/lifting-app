1. What this system is

A personal progressive-overload tracker. One owner. Workouts require the network. Those two facts do more architectural work than any framework choice.

Scale model. This is not a multi-tenant SaaS. “Scalable” here means: years of one person’s sets stay cheap to scan, a tap in the gym stays snappy, and the security story stays one rule — the row belongs to auth.uid(). We deleted an offline/sync layer that was ~40% of the original design because connectivity during workouts is assumed.

3. How a request actually runs

Auth is split on purpose: the edge refreshes cookies; the app layout decides whether you may enter. Mixing those jobs is a common Next.js footgun.

1. Every matched request

src/proxy.ts

Calls updateSession(). Rotates auth cookies. Does not redirect. Static assets and HMR are excluded.

2. Signed-in shell

(app)/layout.tsx

getClaims(). No claims → /login. This is the real gate. Server Actions repeat it.

3. Page load

Server Component

Fetches with the cookie-based public client. RLS still applies. HTML ships with data already in it.

4. User intent

Server Action

Log a set, save a program, pin a lift. Same user client. Revalidate the route after the write.

Memoized once per request

createClient()

Layout, page, and nested loaders share one Supabase client because cache() keys on argument identity.

Memoized once per request

getCatalogMap()

Seeded templates + this owner’s machine variants and customs. Every screen that names an exercise uses the merge.

Memoized once per request

getCurrentBodyweight()

Newest dated weigh-in, else the profile baseline. Live loads use this; historical records never do.

The one exception: weekly Coach API

GET /api/coach/v1/weekly is the only elevated application read path. A scheduled task has no browser session, so it uses a server-held secret client. Every query still includes an explicit COACH_API_USER_ID predicate because that secret bypasses RLS. Capability token, read-only, no-store / noindex. It serializes the same report and proposals Track Coach already shows — it does not invent a second analytics pipeline.

4. The workout loop (where speed is won)

The active session is the product. The architecture around it is: hydrate enough state on the server that the phone can think locally, then write the ledger and rebuild a small cache.

Server hydrates, does not target

Session page

Catalog, user_exercise_stat, recent first-sets, bodyweight, pins, pending Fluid suggestions, workout records.

Client derives instantly

sessionTarget() in useMemo

Swap, edit reps, edit RIR — the suggested load updates with no round-trip. Same helper Coach uses for overload proposals.

Optimistic, then true

logSet action

Inserts set_log (idempotent). Rebuilds that exercise’s stat. Failed writes surface on the card; rest still started.

set_log is the ledger · user_exercise_stat is a rebuildable cache
Rest

Layout-owned timer

Lives in session/[id]/layout.tsx so a set-log revalidation cannot kill it. Absolute end timestamp, not a decrementing counter.

Records

Replay, not a trophy table

Gold PR pills come from workoutRecords over saved sets. Optimistic rows never earn records. Recap is the same replay after finish.

Machines

Resolve before logging

Builder stores a generic template. The session find-or-creates a brand/type variant. Calibration anchors a personal coefficient once, then holds it.

Home, the planner, and Start share loadNextWorkout. That keeps “what is the next day?” from drifting across screens. Planner choices live in a cookie for this browser; they are not a second program.

6. One engine, two runtimes

src/lib/strength/ is framework-free TypeScript. That is not a style preference. It is how the same math can run in the browser during a set and on the server during a rebuild or a Coach report without drifting.

Normalize

e1rm.ts

Weight × reps × RIR → estimated 1RM via an RPE table. Progressive overload means this number trends up.

Transfer

recommend.ts

One latent strength per movement pattern. Exercise coefficient × pattern strength. Bayesian shrink toward the user.

Progress

progression.ts

Bounded best-recent first set for the exact exercise. Hit the top of the rep range → add the increment.

Adapt

plateau.ts

Fluid programs only. Stall → widen reps, then swap. Shared stall evidence with Coach and monthly review.

same functions · client for interaction · server for authority
Why client

Gym latency

A swap that waited on the network would feel broken. Hydrate stats; compute the target next to the stepper.

Why server

The ledger must be honest

e1RM is stored on the set at write time. Stats rebuild after the insert. Records replay from saved rows, not the mutable cache.

Why pure

One definition, many screens

Home, session, recap, Track, Month, Coach UI, Coach API all import the same helpers. If the formula changed in two places, the app would lie.

7. Architecture considerations we actually made

These are the load-bearing choices. Each one is a bet about where work should happen so the app stays fast for one serious lifter, not for a hypothetical million.

01

Delete the layer you do not operate

No offline database, no sync engine, no second backend. Connectivity during workouts is a product assumption. That removed a huge class of conflict, cache, and identity bugs. The remaining PWA bits (manifest, wake lock, notification worker) are cues, not a local replica.

02

Authoritative writes, derived reads

set_log is the source of truth. Stats, Track cards, Coach facts, and PR pills are functions of that ledger. If a cache is wrong, rebuild it. If a report is wrong, fix the function — do not add a second table that can drift. This is how you stay correct as features multiply.

03

Put compute next to the interaction

Session targets run on the client because the interaction is chatty (swap, nudge reps, change RIR). Aggregation for Track and Coach runs on the server because the dataset is the full history and the UI is a read. Charts are client-only because Recharts needs the DOM; they receive already-shaped series.

04

Scan one user’s history; do not invent caches early

Full-history set_log reads are still cheap at personal scale. Analytics therefore has no materialized views or counter tables. When a screen needs a window (21 Chicago days, last 8 session-bests, seven-day Coach), the window is applied in the loader or the pure helper — not by a new schema. Revisit this only if a specific query becomes slow.

05

Pay for a query once per request

React cache() around the Supabase client, catalog, and current bodyweight means layout + page + nested loaders do not stampede the database. cache() keys on arguments, so the shared client instance is what makes the other two hit. The Coach API client is separate on purpose.

06

Identity is exact; browsing can be fuzzy

Progression, records, and review key on exact exercise (and equipment instance when it exists). Quick history may show a family of machine variants for browsing. Mixing those rules would blend a Cybex press with a Hammer Strength press and invent fake PRs. Exactness is the scalability of truth.

07

RLS is the wall; the Coach API is a guarded door

Every user-owned table is scoped to auth.uid(). The weekly Coach route is the sole exception, and it is still one user, one token, read-only. Never add a second service-role path “just for convenience.” Convenience is how owner isolation dies.

08

Optimistic where the body is waiting; honest when the write fails

Rest starts the moment a set is logged locally. The clock is real even if the network blips. The set itself still has to persist, and a failure is a visible card error — not a silent revert that looks like a dead tap. Records wait for persistence so gold never lies.

09

Keep the UI layer small enough to audit

One overlay (Sheet = native <dialog>), semantic tokens, no animation library, View Transitions for reorder. Server Components stay server by keeping class builders in modules without "use client". A thin UI is a performance choice: less JS on a phone in a rack.
